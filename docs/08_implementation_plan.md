# План реализации MVP

Дата: 2026-05-19
Ветка: `feature/mvp-bootstrap-and-docs-move`

Этот документ — инкрементальный план доведения текущего bootstrap-каркаса до работающего MVP. Он опирается на `02_technical_plan.md` (Фаза 1), `05_prd_mvp.md` (scope) и `07_execution_playbook.md` (режим работы) и привязан к коду, который уже есть в репозитории.

## 1. Исходное состояние

Что уже сделано на ветке:

- backend (FastAPI): контракт API из 7 эндпоинтов, Pydantic-схемы, тесты контрактов;
- frontend (Next.js 16 / React 19): форма, workspace, история/избранное, тесты компонентов;
- инфраструктура: `docker-compose.yml`, CI (`pytest` + `npm lint/test`).

Чего нет:

- **генерация текста** — `backend/app/services/pipeline.py` это заглушка: `_compose_lines()` подставляет ввод в шаблон, частушки не пишутся, рифмы и формы нет;
- **проверка формы** — нет подсчёта слогов, рифмы, структуры AABB;
- **модерация** — `is_safe_input()` это блок-лист из одного слова `badword`;
- **персистентность** — `InMemoryPackStore` теряет всё при рестарте;
- **аудио** — TTS, аранжировок и экспорта mp3/wav нет вообще;
- **форма ввода** — `tone`, `boldness`, сценарии и `count` зашиты в `mvp-form.tsx`.

## 2. Решения по scope (Decision Records)

### DR-1. Базовый TTS входит в MVP

`05_prd_mvp.md` §7 относит «генерацию музыки и AI-пение» к out-of-scope, а `02_technical_plan.md` §14 (Фаза 1) включает TTS, аранжировки и экспорт mp3/wav. Противоречие снимается так:

- **в MVP входит**: ритмизованное TTS-озвучивание + 3 заранее подготовленных backing-трека + экспорт mp3/wav;
- **в MVP НЕ входит**: настоящее нейропение (singing synthesis), генерация музыки, MIDI.

Действие: в `05_prd_mvp.md` §7 нужно уточнить формулировку — out-of-scope именно «AI-пение как ядро продукта» и «генерация музыки», а не базовая TTS-озвучка.

### DR-2. Порядок ценности

Сначала строится текстовое ядро (инкременты 1–3), потому что главная гипотеза продукта (`03_summary.md`) — жанровая точность текста и слой проверки формы. Аудио (инкремент 6) подключается после того, как текст подтверждён как достаточно качественный.

## 3. Режим работы

По `07_execution_playbook.md`: каждый инкремент идёт через TDD (Red → Green → Refactor) и завершается блоком `Changes made`. Минимальный набор проверок на инкремент:

- backend: `pytest -q`, `ruff check app tests`;
- frontend: `npm run test`, `npm run lint`.

API-контракт (`backend/app/schemas.py`, пути эндпоинтов) считается стабильным: расширять можно, ломать существующие поля — нет, пока это не зафиксировано отдельным DR. Это защищает frontend и `tests/test_api_contracts.py`.

## 4. Подготовка окружения (инкремент 0)

- Завести `ANTHROPIC_API_KEY` в `.env.example` и в окружение backend (для инкремента 1).
- Поднять `docker-compose up` и убедиться, что backend и frontend стартуют, `GET /health` отвечает.
- Frontend: учесть предупреждение `frontend/AGENTS.md` — это нестандартный Next.js 16, перед правками frontend читать `node_modules/next/dist/docs/`.

DoD: оба сервиса запускаются локально, CI зелёный на неизменённом коде.

## 5. Инкременты MVP

Формат каждого инкремента — контракт из `07_execution_playbook.md`.

### Инкремент 1. Реальная LLM-генерация текста

- **Цель**: заменить шаблонную заглушку на генерацию настоящих 4-строчных частушек через Claude API.
- **Входные файлы**: `backend/app/services/pipeline.py`, `backend/app/schemas.py`, `backend/pyproject.toml`, `backend/tests/`.
- **Действия**:
  1. Добавить зависимость `anthropic` и чтение `ANTHROPIC_API_KEY`.
  2. Реализовать two-pass генерацию (`02_technical_plan.md` Этап B): сначала план (тема, образ, шутка, рифмующиеся окончания), затем 4 строки по плану.
  3. Генерировать несколько кандидатов на один запрос (`count`).
  4. Вынести prompt'ы в отдельный модуль; заложить prompt caching для системной части.
  5. Обработать сбои API: таймаут, ретраи, понятная ошибка наружу.
- **Что нельзя менять**: сигнатуры эндпоинтов и поля схем `Pack`/`Candidate`/`GeneratePackRequest`.
- **Definition of Done**: `/v1/generate-pack` возвращает осмысленные частушки в форме AABB; есть тесты с замоканным клиентом Claude; `pytest`/`ruff` зелёные.
- **Примечание**: использовать skill `claude-api` — он требует prompt caching и знает актуальные модели.

### Инкремент 2. Слой проверки формы и ранжирование

- **Цель**: добавить формальную проверку частушечной формы — это заявленный moat продукта.
- **Входные файлы**: `backend/app/services/` (новый модуль валидации), `pipeline.py`, тесты.
- **Действия**:
  1. Подсчёт слогов по строкам и проверка частушечного метра.
  2. Проверка рифмы (ориентиры из `02_technical_plan.md` §17: `rupo`, `pymorphy2`, инструменты ударений).
  3. Проверка структуры AABB и длины строк.
  4. Заменить фейковый скоринг (`1 - index*0.03`) на реальный composite-score по форме.
  5. Этап `repair` для лучшего кандидата (Этап E техплана) — опционально, можно вынести в инкремент-добавку.
- **Что нельзя менять**: поле `score` остаётся `float`, поле `safe` — `bool`.
- **Definition of Done**: кандидаты с плохой формой получают низкий score и не попадают в топ; тесты на слоги/рифму/структуру зелёные.

### Инкремент 3. Реальная модерация и safe-mode

- **Цель**: заменить блок-лист из одного слова на настоящий safe-by-default режим.
- **Входные файлы**: `pipeline.py` / новый модуль модерации, `routes.py`, тесты.
- **Действия**:
  1. Проверка ввода (`occasion`, `target`, `facts`) на запрещённые темы.
  2. Проверка сгенерированного текста перед выдачей.
  3. `safe_mode=true` по умолчанию; `boldness` ограничивается в safe-режиме.
  4. Понятные коды ошибок (`422 unsafe_input` уже есть — расширить детализацию).
- **Что нельзя менять**: контракт ошибки `422` для небезопасного ввода.
- **Definition of Done**: небезопасный ввод и небезопасный вывод блокируются; тесты на токсичный/политический контент зелёные.

### Инкремент 4. Персистентность (Postgres)

- **Цель**: убрать потерю истории и избранного при рестарте.
- **Входные файлы**: `pipeline.py` (`InMemoryPackStore`), `routes.py`, `docker-compose.yml`, `pyproject.toml`.
- **Действия**:
  1. Добавить сервис Postgres в `docker-compose.yml`.
  2. Схема таблиц для паков, кандидатов, истории, избранного, метрик.
  3. Реализовать `PackStore` поверх БД с тем же интерфейсом, что у `InMemoryPackStore`.
  4. Миграции; строка подключения через env.
- **Что нельзя менять**: интерфейс store, который дёргает `routes.py`.
- **Definition of Done**: история/избранное переживают рестарт; тесты идут на тестовой БД; `/v1/metrics` считает по БД.

### Инкремент 5. Полная форма ввода

- **Цель**: вывести в UI поля, которые сейчас зашиты в `mvp-form.tsx` (требование `05_prd_mvp.md` §6.2).
- **Входные файлы**: `frontend/src/components/mvp-form.tsx`, `mvp-workspace.tsx`, `frontend/src/lib/types.ts`, тесты компонентов.
- **Действия**:
  1. Пресеты сценариев: день рождения, свадьба, юбилей, корпоратив, по приколу.
  2. Контролы для `tone`, `boldness` (0–5), `safe_mode`, `count` (3–20).
  3. Валидация на клиенте до отправки.
  4. Перед правками прочитать `node_modules/next/dist/docs/` (см. `frontend/AGENTS.md`).
- **Что нельзя менять**: форму запроса `GeneratePackRequest` в `types.ts` — она должна совпадать с backend.
- **Definition of Done**: все поля §6.2 управляются из UI; `npm run test`/`lint` зелёные.

### Инкремент 6. Аудио: TTS-озвучка и экспорт

- **Цель**: добавить базовый аудио-слой по DR-1 (Фаза 1 техплана).
- **Входные файлы**: новый модуль аудио в backend, `routes.py`, эндпоинт `/v1/export`, frontend-workspace.
- **Действия**:
  1. Интеграция TTS (OpenAI TTS или локальный Silero/Coqui — `02_technical_plan.md` §17).
  2. 3 заранее подготовленных backing-трека; сведение голоса и трека через `ffmpeg`.
  3. Расширить `/v1/export` форматами `mp3`/`wav` (сейчас только `text`/`json`).
  4. В UI: выбор аранжировки, проигрывание и скачивание аудио.
  5. Рендер аудио сделать асинхронным (очередь), чтобы не блокировать запрос.
- **Что нельзя менять**: существующие форматы экспорта `text`/`json`.
- **Definition of Done**: пользователь получает mp3/wav частушки с фоновым треком; тесты на новые форматы экспорта зелёные.

## 6. Мост в Фазу 2 (после MVP)

Не входит в MVP, но планируется сразу после (`02_technical_plan.md` Фаза 2):

- offline eval set и метрики качества текста;
- улучшенный rhyme scorer и style ranker;
- системный `repair`-pass;
- расширение кнопок доработки.

Фаза 3 (настоящее пение, лицензированные голоса, MIDI) — отдельный горизонт, в этот план не входит.

## 7. Порядок и зависимости

```
Инкремент 0 (окружение)
   └─> 1 (LLM-текст) ─> 2 (проверка формы) ─> 3 (модерация)
                                                   └─> 4 (персистентность)
   5 (форма ввода)  — можно параллельно с 1–4
   6 (аудио)        — после 1–3 (нужен стабильный текст)
```

Критический путь — инкременты 1→2→3: они отвечают на главный вопрос «способен ли сервис стабильно выдавать хорошие частушки». Инкремент 5 независим и может идти параллельно. Инкремент 6 — последний, после подтверждённого текста.

## 8. Главные риски

1. **Качество текста** — LLM может не держать частушечную форму; снижается строгой проверкой в инкременте 2 и multi-candidate + repair.
2. **Права и лицензии** — голоса TTS, backing-треки, лицензии моделей; проверять до инкремента 6 (`02_technical_plan.md` §13).
3. **Культурно-чувствительный контент** — закрывается safe-by-default в инкременте 3.
4. **Себестоимость** — вызовы LLM и TTS на каждый пак; нужен учёт расхода и prompt caching с инкремента 1.
5. **Нестандартный Next.js 16** — `frontend/AGENTS.md` предупреждает о breaking changes; перед любыми правками frontend читать локальные доки.
